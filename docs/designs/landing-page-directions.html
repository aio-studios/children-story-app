Behind the build

Storykins is a solo build — product, architecture and code. Here's what's actually under it.

~20sstory to screen
2AI vendors, swappable
$0infra at current load
Next.js App Router TypeScript Tailwind Claude Haiku Gemini 2.5 Flash Image Supabase + RLS Upstash Redis Vercel Blob

Safety is a layer, not a prompt

Input and output both pass a content-safety pass before anything reaches a child. Model instructions alone were not treated as a control.

Rate limiting is shared, not per-instance

Serverless functions don't share memory, so an in-process limiter protects nothing. Moved to a Redis sliding window keyed per IP.

Illustration is opt-in

Text costs a fraction of a cent; an image costs about four. The expensive call is a toggle the user owns, not a default.

My recommendation

C, with B's demo dropped into its hero.

Picking A is choosing to be safe on the one page whose entire job is to not be forgettable. Picking B alone means betting the first impression on an animation, with nothing behind it if someone's on a bad connection or has reduced-motion on.

C is the only one that admits who's actually reading it. A recruiter is not going to sign up and generate a bedtime story — they're going to scroll, decide whether you can build, and leave. C gives them that without making the product look like a demo. And the "Behind the build" section is genuinely cheap for you, because that content already exists in your plan docs, issue history and case study.

  • Take from B: replace C's static screenshot row with the scripted write-a-story demo. That's the "shows, doesn't tell" moment, but now it has a real pitch above it if it fails.
  • Keep from A: the trust strip and the story excerpt — both cost nothing and make it feel like a shipped product rather than a portfolio entry.
  • Watch: everything in "Behind the build" has to stay true. Numbers on a landing page rot. Anything that will drift gets a link, not a figure.
